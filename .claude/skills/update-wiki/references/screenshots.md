# Screenshots for the wiki

Every published screenshot is **generated by a script in `tmp/`**, never captured
by hand from a live window. That is what lets an image be regenerated after a UI
change without anyone remembering how the original was set up — and it is why a
shot must never depend on the operator's own preferences, data, or hardware.

## The three generators

| Script | Captures | Writes to |
|---|---|---|
| `tmp/generate_wiki_screenshots.m` | Whole windows: Protocol Designer, RunExpt, Self-Test, behavior GUIs, StimPlayer, calibration, Teensy designer | `<wiki>/images/`, and a second copy into `documentation/*/images/` for the three shots the repo also publishes |
| `tmp/generate_component_screenshots.m` | One `obj/+gui/` component per image, in a bare figure sized to it | `<wiki>/images/components/` |
| `tmp/generate_protocol_designer_screenshots.m` | Protocol Designer main window + Interfaces dialog, from the expression/pairs fixture | `documentation/design/images/` only |

Both wiki generators take the same options:

```matlab
generate_wiki_screenshots(Only=["RunExpt","SelfTest"])
generate_component_screenshots(Only=["SyringePump"], NumTrials=150, Seed=7)
generate_component_screenshots(OutputDir='C:\some\other\place')
```

`Only=` is how you regenerate one stale image instead of twenty — the run is
minutes per shot, and every image you rewrite is a binary diff in the wiki repo.

## Running them

Screenshots need **`matlab -batch`**, not the MATLAB MCP server: `exportapp`
capture is the one job the server's persistent `nodesktop` session cannot do
(CLAUDE.md says so explicitly). `-sd` and the server's initial working folder are
both ignored on this machine, so **pass absolute paths**.

```powershell
# everything
matlab -batch "run('C:\src\epsych2\tmp\generate_wiki_screenshots.m')"

# one shot, which needs the function on the path first
matlab -batch "addpath('C:\src\epsych2\tmp'); generate_wiki_screenshots(Only=[""RunExpt""])"
matlab -batch "addpath('C:\src\epsych2\tmp'); generate_component_screenshots(Only=[""SyringePump"",""History""])"
```

Each shot prints its name, the file size, and the path. A failure prints
`FAILED: <message> (<frame>)` and the run continues to the next shot — **read the
tail of the output**. A failed shot leaves the previous image in place, so the
build looks like it succeeded while publishing a stale picture.

The run takes a few minutes (it simulates a 150-trial detection session first)
and is safe to run while the user is working: figures are `Visible='off'`, data
goes to `tempdir`, and every `getpref` group the components touch is snapshotted
and restored on exit. Do not "improve" any of that away.

## Adding a shot for a new component

In `tmp/generate_component_screenshots.m`:

1. Add a row to the `shots` cell: `'YourComponent', @shotYourComponent`. The name
   is the file name (`images/components/YourComponent.png`) and the `Only=` key.
2. Write the `shotYourComponent(S)` local function. It returns the figure; the
   loop exports and closes it.
   - Size the figure to the component: `fig = shotFigure([w h])`. Nothing else is
     in the frame, so the shot should be tight.
   - Most components need a layout cell, not a bare figure — hand them a
     `uigridlayout` with a small `Padding`, or they take a default position and
     lay out off-screen (`gui.SessionClock` is the worked example).
   - Use the shared session `S` — `S.RUNTIME`, `S.DATA`, `S.Psych`, `S.Level`,
     `S.TrialsEvent` — so every image shows the *same* simulated 150-trial
     detection session. Never build your own data.
   - Event-driven components show nothing until data arrives: call `pushData(S)`,
     `pushTrial(S)`, or `replayTrials(S)` (the last only for components that build
     their display from the per-trial sequence).
   - Show the *interesting* state, not the empty one: stage an uncommitted edit,
     select a phase, set a mode lamp, run the timer a couple of seconds. The
     caption on the page will describe exactly this.
   - If the shot owns objects the figure does not (an interface mock, a panel
     object, a `gui.BehaviorGUI`), park them in `fig.UserData` — `closeFigure` deletes
     what it finds there, and otherwise their listeners and timers leak.
3. If the component writes preferences, add its group to `snapshotPrefs` and pass
   an explicit `PreferenceTag='wikiShot<Name>'`. A shot that reads the developer's
   saved column layout is not reproducible, and one that writes theirs is rude.
4. Hardware-backed components run against a mock (`NE1000_Mock`), never a real
   device — the shot must work on a machine with nothing plugged in.
5. Add the matching `### gui.YourComponent` section to `Behavior-GUI-Components.md`:
   image, italic caption, **Purpose**, **Implementation**, a code snippet, and a
   `Reference:` link to the `documentation/gui/` doc.

For a whole-window shot in `generate_wiki_screenshots.m` the shape is the same,
except the shot function returns `[fig, cleanupFcn]` and is responsible for
closing whatever it opened (`closeDesigner`, `closeRunExpt`, `closeByName`).

## Captions

Below every image, one italic line, describing the *specific state in the shot* —
not what the component is for:

```markdown
![gui.Parameter_Control](images/components/Parameter_Control.png)

*Five controls over one protocol: an edit field, a second edit field, a `range`
pair binding `[Min Max]` on one row, a checkbox bound to `isRandom`, and a
momentary trigger button. The green field has been edited but not committed.*
```

This is the part that goes stale invisibly. When a shot changes, re-read its
caption and the sentence around it — the RunExpt caption names the two subjects
and the boxes they sit in, and the Behavior-GUI-Components intro asserts the shots
came from a simulated 150-trial session.

## After regenerating

- `git -C <wiki> status` — an image that changed size by a few bytes is normal
  (timestamps, antialiasing); an image that did *not* change when you expected it
  to means the shot failed or `Only=` missed it.
- Open the new PNGs and look at them. A component that failed to receive data
  renders as an empty axes, and that exports perfectly happily.
- Images copied into `documentation/*/images/` are a code-repo change: commit them
  there with `/commit`, separately from the wiki commit.
